# GitHub authentication

Milestone 5 implements GitHub OAuth App authorization entirely in the Rust
backend. React receives only public account data and structured status/errors;
authorization codes, access tokens, refresh tokens, PKCE verifiers, and the
OAuth App client secret never cross IPC.

## OAuth App setup

Create a GitHub **OAuth App** and set its authorization callback URL to:

```text
http://127.0.0.1/oauth/callback
```

GitHub permits a loopback redirect to substitute an ephemeral port. Branchcraft
binds only `127.0.0.1:0`, then sends the selected port in the authorization
request. It deliberately uses the IPv4 literal instead of `localhost`.

Provide the OAuth configuration while building a distributable binary:

```bash
export BRANCHCRAFT_GITHUB_CLIENT_ID=your_client_id
export BRANCHCRAFT_GITHUB_CLIENT_SECRET=your_client_secret
cargo tauri build --config src-tauri/tauri.conf.json --bundles rpm
```

The equivalent Windows Developer PowerShell commands are:

```powershell
$env:BRANCHCRAFT_GITHUB_CLIENT_ID = "your_client_id"
$env:BRANCHCRAFT_GITHUB_CLIENT_SECRET = "your_client_secret"
cargo tauri build --config src-tauri/tauri.conf.json --bundles nsis
```

The same variables can be supplied at runtime for local development. Runtime
values take precedence over values embedded by `option_env!`. A build without
both values remains fully usable for local Git work and reports GitHub sign-in
as unconfigured.

## Current GitHub constraint

GitHub recommends PKCE for OAuth Apps and supports `S256`, but its OAuth App
token endpoint still requires `client_secret`. GitHub also explicitly notes
that native apps cannot keep that value confidential. Branchcraft therefore
uses the required value as public application configuration and does not claim
it is a security boundary. Do not reuse a secret that protects another client
or service.

The authorization code is instead protected by:

- a fresh 256-bit PKCE verifier and `S256` challenge per login, generated by a
  CSPRNG seeded from the operating system;
- a fresh 256-bit CSRF `state` from the same CSPRNG, checked in constant time;
- an HTTP listener bound only to `127.0.0.1` on an ephemeral port;
- a five-minute overall timeout and bounded callback request parsing;
- exact callback path and HTTP method validation.

The requested scopes are `repo offline_access`. `repo` authorizes the
authenticated HTTPS Git operations implemented in Milestone 6;
`offline_access` requests refresh-token support when token expiration is enabled
for the OAuth App.

- [GitHub: Authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)
- [GitHub: OAuth app best practices](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/best-practices-for-creating-an-oauth-app)
- [GitHub: OAuth app scopes](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)

## Runtime flow

```text
AccountMenu
    -> typed Tauri auth command
    -> AuthService
    -> bind 127.0.0.1:<ephemeral>
    -> system browser / GitHub authorization
    -> validate callback state and exchange code with PKCE
    -> GitHub REST GET /user
    -> SecretStore
    -> native SecretStore
       -> Fedora Secret Service / GNOME Keyring
       -> Windows Credential Manager
```

The callback page has a restrictive content security policy, contains no
credential data, and tells the user to return to Branchcraft. Browser launch,
listener, denial, malformed callback, state mismatch, timeout/cancellation,
network, token exchange, GitHub API, and keyring failures map to explicit safe
errors.

Branchcraft requests the current user through GitHub's `GET /user` endpoint
using API version `2026-03-10`. A stored token is validated when authentication
status is loaded. Unauthorized credentials are removed. Expiring access tokens
are refreshed shortly before expiry, and rotated refresh tokens replace the
previous stored session.

The repository browser requests accessible repositories through the paginated
`GET /user/repos` endpoint with the same backend-only access token. Only public
repository metadata crosses IPC; the token remains inside Rust. Repository
cloning likewise obtains the token only after the clone source has been
classified as exact, credential-free GitHub HTTPS. Public non-GitHub HTTPS
sources are cloned anonymously.

## Secret storage and logout

The complete OAuth token set is serialized only in memory and passed to the
`SecretStore` abstraction as a `SecretString`. Production uses `keyring` 4.2;
its native backend talks to Secret Service over zbus on Fedora and Windows
Credential Manager on Windows. Tokens are never written to application
configuration, Git configuration, SQLite, frontend storage, remote URLs,
process arguments, or logs.

Ordinary CI runs the reusable `SecretStore` contract against an in-memory fake
and tests OAuth with fake browser/GitHub adapters. A real desktop keyring can
require an unlocked interactive session, so persistence and logout are covered
by the Fedora and Windows release smoke tests instead of weakening headless CI.

For fetch, pull, and push, the desktop command requests an access token only
after the Git backend classifies the active remote as credential-free GitHub
HTTPS. The token stays in a backend `SecretString`, is passed to libgit2's
credential callback as the HTTPS password, and is discarded after the worker
finishes. Redirects and credential-bearing remote URLs are rejected to prevent
credential forwarding. GitHub documents that HTTPS Git accepts a personal or
OAuth token in the password position with a nonempty username; Branchcraft uses
the conventional `x-access-token` username.

Logout cancels a pending login and deletes the local keyring item. It does not
revoke the OAuth App authorization on GitHub; users can revoke that grant in
GitHub account settings when server-side revocation is desired.
